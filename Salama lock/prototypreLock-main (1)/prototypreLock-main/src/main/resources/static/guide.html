Salama Lock

Full system guide

How a finance company uses the API key you issued to lock a customer’s phone — including a full partner API handbook — what JSON your middleware receives, where each field is stored, and what gets sent to Google DLC (mocked today).

1. Start the stack on localhost

cd /home/edison/salama_lock
docker compose up -d
mvn spring-boot:run
  • App: http://localhost:8080/
  • Issue key: http://localhost:8080/admin
  • See DB rows: http://localhost:8080/admin/data
  • Postgres: localhost:5432 / user salama / pass salama / db salama_lock

2. End-to-end story

  1. You onboard Acme Finance and give them an API key (admin page).
  2. Acme’s system registers the phone (imei1/imei2) and stores the returned permanent lockId.
  3. Customer defaults → Acme calls POST /api/v1/lock with that lockId.
  4. Middleware saves a command as PENDING (does not call Google yet).
  5. Background worker picks the command, loads identifiers, and calls MockGoogleProvider with lock_id + primary IMEI.
  6. On success, device status becomes LOCKED and command SUCCESS.

3. Partner company API handbook

This section is what you hand to a finance / retail partner after you issue their API key. Base URL (local): http://localhost:8080

3.1 What you receive from Salama

  • A secret API key (shown once) — store it in your vault / secrets manager.
  • Your company code (e.g. ACME).
  • Scopes on the key (default): devices:read, devices:write, commands:read, commands:write.
Never put the API key in mobile apps, public repos, or frontend JavaScript. Only your backend (loan / CRM / finance system) should call Salama Lock.

3.2 Authentication (every partner request)

Send one of the following on every protected call:

MethodHeaderWhen to use
API key X-Api-Key: sk_live_… Simplest — recommended for server-to-server
JWT Authorization: Bearer <token> After exchanging the API key for a short-lived token

Exchange API key → JWT (optional):

curl -s -X POST http://localhost:8080/api/v1/auth/token \
  -H "X-Api-Key: YOUR_API_KEY"

Example response:

{
  "accessToken": "eyJhbGciOi…",
  "tokenType": "Bearer",
  "expiresInSeconds": 3600,
  "companyCode": "ACME",
  "scopes": ["devices:read","devices:write","commands:write","commands:read"]
}

Missing/invalid credentials → 401. Valid auth but missing scope → 403.

3.3 Recommended integration sequence

  1. At device sale / loan start — register the device (imei1/imei2). Store the returned permanent lockId (ULID, e.g. SL-01K5A8FYD4QQ8E4T2G5S6H1C8P).
  2. On default / collections trigger — POST /api/v1/lock with lockId.
  3. Poll GET /api/v1/commands/{commandId} (from Location / links.self; respect pollAfterSeconds) until SUCCESS or FAILED.
  4. When loan is cured — POST /api/v1/unlock with lockId.
  5. When device leaves your program — DELETE /api/v1/devices/{lockId} (soft deactivate).

3.6 Lock a device

curl -s -X POST http://localhost:8080/api/v1/lock \
  -H "X-Api-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -H "X-Correlation-Id: acme-loan-77821" \
  -d '{
    "lockId": "SL-01K5A8FYD4QQ8E4T2G5S6H1C8P",
    "idempotencyKey": "loan-77821-lock",
    "externalRef": "LOAN-77821"
  }'
FieldRequiredNotes
lockIdpreferredPermanent Salama lock id from registration
imeitransitionalAllowed only when salama.identity.allow-imei-lock=true
idempotencyKeystrongly recommendedSame key + company returns the same command (safe retries)
externalRefnoYour loan / invoice / case id

Response is 202 Accepted immediately. The lock is queued (status: PENDING) — Google is called by Salama’s worker a moment later.

{
  "commandId": "632055db-9711-4a98-b9bc-5b0ade778f74",
  "lockId": "SL-01K5A8FYD4QQ8E4T2G5S6H1C8P",
  "commandType": "LOCK",
  "status": "PENDING",
  "provider": "GOOGLE_DLC",
  "externalRef": "LOAN-77821",
  "idempotencyKey": "loan-77821-lock",
  "correlationId": "acme-loan-77821",
  "createdAt": "2026-07-23T08:45:11Z",
  "pollAfterSeconds": 2,
  "links": {
    "self": "/api/v1/commands/632055db-9711-4a98-b9bc-5b0ade778f74",
    "device": "/api/v1/devices/SL-01K5A8FYD4QQ8E4T2G5S6H1C8P"
  }
}

Send X-Correlation-Id on the request (recommended). Salama stores it on the command, echoes it in the JSON body, and always returns it as a response header. Follow the Location header (or links.self) to poll status. While non-terminal, pollAfterSeconds suggests how long to wait before the next poll (omitted on SUCCESS / FAILED).

Command status lifecycle

PENDING → PROCESSING → SUCCESS

PENDING → PROCESSING → RETRYING → PROCESSING → … → SUCCESS
                                         ↘ FAILED (retries exhausted)

PENDING → PROCESSING → FAILED   (non-retryable provider error)
StatusMeaning
PENDINGQueued, not sent to Google yet
PROCESSINGWorker is calling the provider
RETRYINGProvider unavailable; will retry (30s → 1m → 5m → 15m)
SUCCESSTerminal success — device status updated (LOCKED / UNLOCKED)
FAILEDTerminal failure — see errorCode / errorMessage

Poll until SUCCESS or FAILED. Do not treat RETRYING as final.

Future: partner webhooks

Today partners poll GET /commands/{id}. A later release may add POST /api/v1/webhooks so Salama can push terminal results to your URL (e.g. POST https://partner.example.com/webhooks/device-lock) after Google DLC completes. Polling will remain supported; webhooks reduce latency and load for high-volume partners.

Deactivated / retired / suspended devices cannot receive new lock/unlock commands (409 DEVICE_NOT_COMMANDABLE).

3.10 Idempotency & safe retries

  • Always send a stable idempotencyKey per business action (e.g. {loanId}-lock).
  • If your HTTP client times out, retry the same key — Salama returns the original command instead of locking twice.
  • Use a different key for unlock vs lock.

3.13 Minimal partner checklist

  1. Store API key securely; never ship it to phones.
  2. Register device at loan origination with imei1/imei2; store the returned Salama lockId.

7. What is passed to Google DLC

CommandExecutorService builds a versioned ProviderCommandRequest from stored DB data (not from a second partner call): permanent lockId, identifier map, metadata, and provider hints. 

{
  "schemaVersion": 1,
  "lockId": "SL-01K5A8FYD4QQ8E4T2G5S6H1C8P",
  "identifiers": { "IMEI": "359759002014300", "IMEI2": "…", "SERIAL": "…" },
  "commandType": "LOCK",
  "commandId": "<commands.id>",
  "metadata": { ... },
  "providerHints": { }   // future: androidEnterpriseId, projectId, …
}

Today that goes to MockGoogleProvider. After partnership, the same payload shape is sent by GoogleDlcProvider to Google’s API. Flip system_configs.provider.active from MOCK_GOOGLE_DLC → GOOGLE_DLC.

After a successful mock lock, DB updates:

  • commands.status → SUCCESS, plus provider_request_id + provider_response JSON
  • devices.status → LOCKED
  • audit_logs gets HTTP + worker rows

Unlock requests follow the same request format as lock requests. Use lockId as the primary device identifier; imei is accepted only for backward compatibility when salama.identity.allow-imei-lock=true. Use a new idempotencyKey (never reuse the lock key).

New integrations should always use lockId. IMEI support exists only for backward compatibility and may be removed in a future release.

If both lockId and imei are supplied, they must identify the same device; otherwise the request is rejected with 400 LOCK_ID_MISMATCH.

12. Architecture layers (production rule)

Controller → HTTP only (no DB access) ↓ Service → business logic + transactions ↓ Provider → Google DLC / Mock (when needed) ↓ Repository → persistence ↓ Database

The external partner identity (lockId) is immutable. Hardware identifiers (IMEIs, serials, Google IDs) may change over the lifetime of a device and are therefore stored separately in device_identifiers.

Controllers never inject repositories or write to the database. Example lock path: CommandController → CommandService → (queue) → CommandExecutorService → DeviceLockProvider → DB via repositories.

Production checklist

  1. Run with SPRING_PROFILES_ACTIVE=prod.
  2. Set strong secrets from env (see .env.example): JWT_SECRET, SALAMA_ADMIN_API_KEY, SALAMA_CALLBACK_SECRET.
  3. Terminate TLS at a reverse proxy (nginx / cloud LB) — HTTPS only.
  4. Put the app in a private network; expose only the API gateway.
  5. Restrict DB to the app subnet; no public Postgres.
  6. Set CORS_ALLOWED_ORIGINS to your real admin origin(s) only.
  7. Rotate partner API keys if leaked; revoke via api_keys.status=REVOKED.
  8. After Google partnership: verify callback signatures per Google’s docs (beyond shared secret).
  9. Add WAF / rate limits at the edge (per IP + per API key).
  10. Ship structured audit logs to SIEM; alert on repeated 401s.

What partners must do

  • Keep API keys only on their backend — never in mobile apps or browsers.
  • Use HTTPS to your API.
  • Send idempotencyKey on lock/unlock.
  • Treat 401 as “rotate credentials / check vault”.
