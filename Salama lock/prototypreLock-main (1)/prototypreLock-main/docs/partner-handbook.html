Integration guide

Partner Handbook

End-to-end partner integration: authentication, registration, lock/unlock, polling, errors, idempotency, and correlation IDs.

1. Authentication

Two supported partner credentials:

  1. API key on every request — header X-Api-Key: sk_live_…
  2. JWT Bearer — exchange key at POST /api/v1/auth/token, then Authorization: Bearer <token>
# Exchange
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/token \
  -H "X-Api-Key: $API_KEY" | jq -r .accessToken)

# Use
curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/devices

Default scopes: devices:read, devices:write, commands:write, commands:read.

Missing auth → 401. Valid auth missing scope → 403 Insufficient scope.

2. Registration

At loan origination / sale, register the device. Always store the returned lockId.

curl -s -X POST http://localhost:8080/api/v1/devices \
  -H "X-Api-Key: $API_KEY" -H "Content-Type: application/json" \
  -H "X-Correlation-Id: loan-origin-1001" \
  -d '{
    "imei1": "359759002014300",
    "imei2": "359759002014318",
    "manufacturer": "Samsung",
    "model": "A54",
    "metadata": { "loanId": "LOAN-22" }
  }'
  • Salama generates permanent lockId like SL-01K5A8FYD4QQ8E4T2G5S6H1C8P (never derived from IMEI).
  • Client-supplied lockId in the body is ignored.
  • Duplicate active identifier for your company → 409 DEVICE_EXISTS.
  • Same IMEI under another company is allowed (portfolio transfer).
  • Initial status: REGISTERED.

3. Lock

curl -s -X POST http://localhost:8080/api/v1/lock \
  -H "X-Api-Key: $API_KEY" -H "Content-Type: application/json" \
  -H "X-Correlation-Id: collect-INV-1001" \
  -d '{
    "lockId": "SL-01K5A8FYD4QQ8E4T2G5S6H1C8P",
    "idempotencyKey": "fin-inv-1001-lock",
    "externalRef": "INV-1001"
  }' -i

Expect 202, Location: /api/v1/commands/{id}, body with status: PENDING and pollAfterSeconds.

Rejected when device status is SUSPENDED, DEACTIVATED, or RETIRED → 409 DEVICE_NOT_COMMANDABLE.

4. Unlock

Same contract as lock with a new idempotency key:

curl -s -X POST http://localhost:8080/api/v1/unlock \
  -H "X-Api-Key: $API_KEY" -H "Content-Type: application/json" \
  -d '{
    "lockId": "SL-01K5A8FYD4QQ8E4T2G5S6H1C8P",
    "idempotencyKey": "fin-inv-1001-unlock",
    "externalRef": "INV-1001"
  }'

5. Polling

  1. Read Location or links.self.
  2. Call GET /api/v1/commands/{commandId} with commands:read.
  3. Wait at least pollAfterSeconds between polls while status is PENDING / PROCESSING / RETRYING.
  4. Stop on SUCCESS or FAILED (pollAfterSeconds omitted).
curl -s http://localhost:8080/api/v1/commands/$COMMAND_ID \
  -H "X-Api-Key: $API_KEY"
StatusMeaningPartner action
PENDINGQueuedPoll later
PROCESSINGWorker calling providerPoll later
RETRYINGRetryable provider failurePoll; inspect nextRetryAt
SUCCESSTerminal OK; device LOCKED/UNLOCKEDDone
FAILEDTerminal errorInspect errorCode/message; decide retry with new idempotency key
There is no partner webhook push API in the current codebase. Polling is the integration path. (Legacy guide mentions future /api/v1/webhooks — not implemented.)

6. Idempotency

  • Optional idempotencyKey (max 128), unique per company (uq_commands_company_idempotency).
  • Replaying the same key returns the existing command response (no second enqueue).
  • Use distinct keys for lock vs unlock of the same loan event.

7. Correlation IDs

  • Send X-Correlation-Id on partner requests.
  • HttpAuditFilter generates a UUID if absent, sets request attribute, and echoes the header on the response.
  • Lock/unlock persist the correlation id on commands.correlation_id (migration V5) and return it in CommandResponse.correlationId.
  • Exposed CORS header: X-Correlation-Id.

8. Device lifecycle for partners

StatusAccepts lock/unlock?How reached
REGISTEREDyesAfter registration
ACTIVEyesAllowed by schema; not set by current happy-path code
UNLOCKEDyesSuccessful UNLOCK (or callback UNLOCKED)
LOCKEDyesSuccessful LOCK (or callback LOCKED)
UNKNOWNyesAllowed; not set by current flows
SUSPENDEDnoOperational hold (not set by partner delete)
DEACTIVATEDnoDELETE /devices/{lockId}
RETIREDnoTerminal; deactivate is no-op if already retired

DeviceStatus.acceptsCommands() returns false only for SUSPENDED, DEACTIVATED, RETIRED.

9. IMEI fallback (transitional)

If salama.identity.allow-imei-lock=true (default), lock/unlock may omit lockId and send imei. Prefer lockId for all new integrations. When both are sent, imei must match an IMEI on that device or 400 LOCK_ID_MISMATCH.

10. Errors

See the full table in API Reference → Error reference. Always parse error + message; use details for validation.

11. Best practices

  • Persist lockId as your foreign key to Salama — never invent lock IDs.
  • Always send idempotencyKey and X-Correlation-Id from your loan/invoice id space.
  • Respect pollAfterSeconds; do not busy-poll.
  • Treat RETRYING as in-flight, not failure.
  • Soft-deactivate with DELETE when the device leaves your program.
  • Do not rely on partner monitoring endpoints for multi-tenant isolation (global counts).
  • Rotate API keys via admin processes; raw keys are shown once at creation.
